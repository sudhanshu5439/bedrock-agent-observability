Bedrock Agent Observability · demo architecture

Read it top to bottom: a request leaves the laptop, reaches one of two agents (classic Bedrock Agent or AgentCore), and every step it takes is recorded inside the AWS account. The dashboard at the bottom reads those records back, so for any agent we can answer what it is, what it did, who asked, what it cost and where it failed.

Account: shared company AWS account Region: us-east-1 Model: Claude Haiku 4.5 Status: All phases done · 3 Nov 2026

Flow 1 · A request, and the evidence it leaves

  1. 1The presenter types a question in the dashboard's Live test tab, or the traffic generator sends a batch of scripted prompts.
  2. 2The invoke wrapper calls InvokeAgent with enableTrace=true (classic) or InvokeHarness (AgentCore; CloudTrail records it as InvokeAgentRuntime).
  3. 3The guardrail screens the input and, later, the answer: it masks emails and phone numbers and refuses the denied topic.
  4. 4The agent asks Claude Haiku 4.5 what to do next.
  5. 5The agent calls a tool (the hr-tools Lambda for HR; for IT, an MCP call through AgentCore Gateway to the it-tools Lambda) and loops through 4–5 until it can answer.
  6. 6CloudTrail records the invoke call as a data event: who called, when, from which IP, against which agent.
  7. 7Model invocation logging writes every model call's prompt, response and token counts to CloudWatch Logs, with a copy in S3.
  8. 8The step-by-step record is kept: classic trace events come back to the wrapper, which saves them to DynamoDB; AgentCore emits OpenTelemetry spans that Transaction Search stores in aws/spans.
  9. 9CloudWatch publishes invocations, latency, tokens, errors and throttles as metrics.

Flow 2 · Investigating an agent in the dashboard

  1. APick an agent. Its configuration (instructions, model, tools, guardrail, versions) is read live from the Bedrock Agent and AgentCore control APIs.
  2. BHealth over time: invocations, latency, tokens and errors from CloudWatch metrics.
  3. COpen a session: a step timeline built from DynamoDB (classic) or from spans (AgentCore): question, reasoning, tool call with inputs and outputs, answer.
  4. DSee exactly what the model was sent and what it replied, with tokens and estimated cost, from the invocation logs.
  5. EAudit: who invoked the agent (demo trail) and who changed it (company trail), with time and source IP.
  6. FEvery guardrail block, masked field and failed call in one list, with the reason.

1. What we are building

Our team runs agents on Amazon Bedrock in two styles: classic Bedrock Agents (configured in the console, with action groups and knowledge bases) and Bedrock AgentCore agents (our own code, hosted by AWS). Today there is no single place to see what an agent did, who used it, what it cost, or why it failed.

The demo builds one of each kind of agent from scratch, turns on every recording feature Bedrock offers, and puts a single dashboard on top. It is built to answer five questions for any agent:

Why both types matter right now: AWS has put classic Bedrock Agents into maintenance mode (closed to new customers) and recommends moving to AgentCore, whose Harness is the managed replacement for the classic agent loop. Existing accounts like ours can still run and create classic agents, so for the length of any migration we will operate both side by side. An observability layer that covers both, and that does not change when an agent moves from one to the other, is exactly what that period needs.
  1. What is it? Model, instructions, tools, guardrail, versions.
  2. What did it do? Every step of every session: reasoning, tool calls, data returned, final answer.
  3. Who used or changed it? Caller identity, time, source IP, configuration changes.
  4. How is it performing, and what does it cost? Calls, latency, tokens, errors, estimated spend.
  5. What went wrong? Guardrail blocks, tool failures, throttles, model errors.

Why classic agents need the DynamoDB trace store

A classic Bedrock Agent only returns its step-by-step trace inside the response to InvokeAgent, and only when the caller asks for it with enableTrace=true. AWS does not keep that trace anywhere. The invoke wrapper reads the trace as it streams back and writes each event to DynamoDB, which is what lets the dashboard replay a session later. AgentCore does not need this: its spans are recorded by AWS automatically.

4. Why this approach

The deciding facts: we run both agent types, the lead asked for depth (what the agent actually did, not only that it ran) plus an audit trail, and this is a demo that should not need a purchase or a security review.

Reasons it wins

  1. Only option that covers both agent types. Every alternative leaves a gap in classic agents, configuration or audit.
  2. The groundwork is reusable. CloudTrail data events and invocation logging are the foundation for any tool we pick later, including a paid one. Only the thin dashboard would change.
  3. No procurement, no security review. Data stays in our account under our IAM.
  4. Cheap and reversible. About $6–8 for the demo week, a budget alarm, and one teardown script.
  5. Low risk. The dashboard only reads. It cannot change how any agent behaves.

Alternatives considered

  • CloudWatch dashboards only. Easy, but cannot show agent configuration or a classic agent's reasoning and tool calls, which is the core of the ask.
  • AgentCore Observability only. Excellent for AgentCore, blind to classic agents.
  • Migrate classic agents to AgentCore first. A real project in its own right, far bigger than a demo.
  • Datadog / Langfuse / Arize. Polished trace views, but licences, data leaving AWS, and we would still write capture code for classic agents. Worth evaluating for production.
  • QuickSight or Grafana. Good charts (the account already uses QuickSight), but neither renders a step-by-step agent trace or agent configuration well.
  • Full pipeline (Kinesis, OpenSearch). Built for scale we do not have yet; weeks of work and standing cost.

7. Working safely in a shared account

The AWS account is shared with other teams and clients, so the build follows three rules:

  • Do not touch what is not ours. Model invocation logging in ap-south-1 belongs to another project, the company trail is used read-only, and existing agents and runtimes are not modified.
  • Region-wide settings only where unused. Invocation logging is one setting per region; we set it in us-east-1, where it was empty. The setup script refuses to overwrite anyone else's configuration.
  • Everything is findable and removable. Every resource is named bedrock-demo-* and tagged Project=bedrock-observability-demo (IAM roles are named but not tagged, because the role lacks iam:TagRole).
Side effect to know about: invocation logging covers the whole us-east-1 region, so model calls from the two other teams' AgentCore runtimes there are also logged to our log group while the demo runs. Teardown switches it off.

8. Limits, and what production would add

  • The dashboard is demo-grade: it runs on a laptop with the presenter's SSO credentials and has no login of its own.
  • Cost figures in the dashboard are estimates from token counts and list prices, not billing data.
  • Classic agent traces are only captured for calls that go through our wrapper. Agents called directly by other applications would need the same capture added there.
  • For production we would host the dashboard behind SSO (or move to AgentCore Observability or a paid tool once agents migrate), add alarms on error and guardrail rates, and set retention to match audit policy. The recording layer underneath stays as it is.
